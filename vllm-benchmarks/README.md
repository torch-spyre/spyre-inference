# Spyre vLLM benchmarks

Benchmark configs for the `vLLM Benchmark` CI workflow and for local runs on Spyre hardware. There is one file per model and bench type, under `benchmarks/decoder/` (decoder models) and `benchmarks/encoder/` (pooling models). `benchmarks/power_use_case/` holds the power-applications configs, one file per workload (`ee`, `rag`, `vision`, `embedding`). The file name is `<bench type>-<model>-runs.yaml`, where `<model>` is the Hugging Face model name without its org (or the workload, in `power_use_case/`), and the prefix picks the command:

- `latency-*-runs.yaml` → `vllm bench latency`
- `throughput-*-runs.yaml` → `vllm bench throughput`
- `serve-*-runs.yaml` → `vllm bench serve` (starts a server, waits for health, then benchmarks against it)

Each file is a `defaults` mapping plus a `tests` list, where each test entry is merged over `defaults` so it only spells out what differs. `SPYRE_DEVICES` / `AIU_WORLD_SIZE` are derived from each entry's tensor-parallel size rather than spelled out per test. A `test_name` must be unique across all files, since it names the result file.

## Suites

Each entry names its suites in `labels`, at least one of:

| Suite | Use |
|---|---|
| `minimal` | A short set for a quick check. |
| `base` | Automated runs (the `vLLM Benchmark` workflow and the `perf` test type) and evaluating a change. |
| `reference` | The configs used for reporting and decisions. |
| `power-applications` | The power use-case workloads (`power_use_case/`). |

`BENCH_SUITE` picks the suite (default `base`). A missing or unknown label fails the run.

The [config tables](#config-tables) below are generated by `.github/scripts/generate_bench_config_tables.py`, run by the pre-commit hook and checked by the `Benchmark config tables` workflow.

A serve `test_name` is `serve_<model>_tp<N>_c<C>_<dataset>`, where `c<C>` is the max concurrency; pooling entries leave out the dataset. The `tp<N>` and `c<C>` parts are the benchmark identity downstream. Decoder serve entries replay a recorded agentic trace, named by the dataset suffix. Latency and throughput entries cannot replay traces, so they use a fixed `in<N>_out<N>` shape; it is part of the benchmark identity downstream, so changing it starts a new trend line.

## Running locally

Benchmarks run through the `perf-tests` Make target. `BENCH_SUITE` picks the suite, and three optional filters narrow it further; a test runs only if it passes all of them:

- `MODELS` — comma-separated model names (matched case-insensitively). Empty =
  all models.
- `TPS` — comma-separated tensor-parallel sizes, e.g. `TPS=1,4`. Empty = all
  sizes.
- `BENCH_TYPES` — comma-separated subset of `latency,throughput,serve`. Empty =
  all types.

```bash
# The base suite (all models, all bench types)
make perf-tests RESULTS_DIR=benchmark-results

# The minimal serve entries of one model, at tensor-parallel 4
make perf-tests RESULTS_DIR=benchmark-results BENCH_SUITE=minimal \
  MODELS=ibm-granite/granite-4.1-8b \
  TPS=4 \
  BENCH_TYPES=serve

# The reference entries of one model
make perf-tests RESULTS_DIR=benchmark-results BENCH_SUITE=reference \
  MODELS=google/gemma-4-26B-A4B

# Every entry of one file, whatever its labels
make perf-tests RESULTS_DIR=benchmark-results \
  BENCH_CONFIGS_DIR=vllm-benchmarks/benchmarks/decoder/serve-granite-4.1-8b-runs.yaml
```
